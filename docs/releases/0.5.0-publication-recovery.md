# SDK 0.5.0 publication recovery

## Recorded state, 22 September 2026

The immutable SDK tag `v0.5.0` resolves to
`5c1b251e6e6351110ddc20606f77408ffb333971`. All four environments passed
[release preparation run 35785771054](https://github.com/rewire-bio/rewire-benchmarks/actions/runs/35785771054).
[Dry run 35786167687](https://github.com/rewire-bio/rewire-benchmarks/actions/runs/35786167687)
verified twelve planned assets. Neither the tag nor those binary artifacts needs rebuilding.

[Publication attempt 35786382909](https://github.com/rewire-bio/rewire-benchmarks/actions/runs/35786382909)
created an empty draft but did not publish or upload assets. Its green Actions
status was incorrect:

1. The script created a draft, then looked it up through `/releases/tags/v0.5.0`.
   That endpoint returned 404 for the draft. Accessing the resulting `None` value
   raised a `TypeError` before the first asset upload.
2. The implicit Bash invocation used `-e` without `pipefail`. The publisher piped
   output to `tee`, whose successful exit hid the publisher failure.
3. The release-creation command wrote its draft URL to standard output, corrupting
   the supposedly JSON-only publication plan.

The draft contains no scientific submission data. Intake, notifications and
scientific dataset publication are unrelated to this package-release operation.

## Recovery behavior

The publication workflow checks out two revisions separately. The publishing
program comes from the workflow's exact commit, which must be clean and already
merged into `origin/main`. A separate checkout validates the unchanged SDK tag.
The publication receipt records `publisher.commit` and `publisher.tree` separately
from the package's `source.source_commit` and `source.source_tree`.

Drafts are found through the paginated release list, filtered by exact tag. New
drafts are created through the API, which returns their release ID directly.
Subsequent reads and publication use that ID. The remote tag must still resolve
to the reviewed SDK source. Existing public releases, conflicting drafts and
mismatched assets remain protected from replacement.

The workflow runs with explicit Bash and `set -euo pipefail`. GitHub CLI output is
captured separately from the JSON plan. A final fresh API read must confirm
`draft: false`, a publication timestamp, the expected tag/source and all twelve
asset names, sizes and SHA-256 values before `publication_status: published` is
emitted. `publish_requested: true` alone is never a success receipt.

## Recovery procedure

After this publisher fix is reviewed and merged:

1. Dispatch **Publish reviewed SDK artifacts** from **main**, using tag `v0.5.0`,
   preparation run `35785771054` and `dry_run=true`.
2. Verify the new small plan. All ten wheel/sdist/OCI/SIF binaries must retain the
   previously reviewed hashes. The validation receipt and its checksum manifest
   gain the reviewed publisher identity; their hashes therefore change.
3. Dispatch the same reviewed workflow from main with `dry_run=false`. It resumes
   the existing identical empty draft. No retagging, binary rebuild or deletion is needed.
4. Independently verify the public release and server digests. Only then install
   the released wheel, run offline SDK checks and add a dated publication record.

This document records the failed attempt and the recovery design. It does not
claim that the recovery has already been dispatched or that v0.5.0 is public.
